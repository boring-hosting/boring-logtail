#+title: How boring-logtail hears a log
#+license: GFDL-1.3-or-later

This page describes the program that exists today.

* The whole trip

#+begin_example
/var/log/pods/NAMESPACE_POD_UID/CONTAINER/RESTART.log
  -> changed-file notification
  -> bounded physical-line read
  -> CRI timestamp / stream / P-or-F parse
  -> bounded partial join
  + node-scoped Pod and ReplicaSet watch
  -> LogRecord with exact workload identity
  -> bounded OTLP queue and batch worker
  -> boring-collector
#+end_example

Kubelet and the container runtime already chose the Kubernetes log boundary.
The agent reads that result instead of guessing from application syscalls.

* Files and rotation

Existing files start at EOF so agent startup does not replay the node. A newly
discovered file starts at zero. The reader keeps an old inode open through
rotation and begins its replacement at zero.

File notifications mark only changed files readable. Creates, removes, and
renames request one debounced reconciliation; they do not run a full tree scan
inline. A slow repair scan covers missed notifications and overflow.

This is live tailing, not durable ingestion. An agent restart can miss bytes
written while it was down. Persisted offsets need their own evidence and spec.

* CRI records

A physical record is =TIMESTAMP STREAM TAG PAYLOAD=. =STREAM= is =stdout= or
=stderr=. =TAG= is =F= for a complete record or =P= for a partial record.
Payload stays opaque bytes; JSON parsing belongs downstream.

Partial lanes are separated by Pod UID, container, restart, and stream. Record
bytes, physical lines, and simultaneous partial lanes are bounded. Truncation
travels with the record instead of becoming invisible loss.

* Kubernetes identity

The path supplies Pod UID and container name. One node-filtered Kubernetes
watch supplies namespace, Pod, container ID, and workload ownership. ReplicaSet
UIDs resolve Deployments without guessing from names. The capture loop reads an
immutable snapshot; it performs no metadata I/O for each record.

Records without current exact identity are skipped and reported. Choosing a
plausible Pod would be worse than admitting uncertainty.

* Delivery and queries

The node exporter has bounded record and byte queues. One worker preserves
batch order, retries for a bounded interval, and counts overload or delivery
failure. A dead collector cannot grow node memory forever or stop file reads.

The collector shares one =Arc<LogStore>= between OTLP ingestion and gRPC
readers. Selectors return retained matches followed by later inserts. This is
connected-session truth, not durable exactly-once delivery.

* The old kernel path

The project once captured =write=/=writev= with eBPF, reconstructed chunks,
resolved cgroups, and framed lines in userspace. It was fast and taught us a
lot, but CRI files are the honest Kubernetes boundary. See
[[file:ebpf.org][the historical eBPF guide]] and the
[[file:../blog/20260816-ebpf-kubernetes-log-scraper.org][retrospective]].
