#+title: How boring-logtail hears a write
#+license: GFDL-1.3-or-later

This page describes the program that exists, not the finished creature from the
roadmap. When code and this page disagree, that is a bug in one of them.

* The whole trip

#+begin_example
application thread
  write(fd, buffer, count)
       |
       | sys_enter_write
       v
  remember WriteStart by PID+TID
       |
       | Linux performs the write
       | sys_exit_write(result)
       v
  create WriteJob
       |
       | tail calls, one bounded copy each
       v
  WriteEvent + WriteEvent + ...
       |
       | BPF ring buffer
       v
  decode_event
       |
       v
  WriteAssembler
       |
       v
  WriteOperation { identity, result, integrity, bytes }
       |
       v
  cgroup snapshot + scoped, node-filtered Pod snapshot(s)
       |
       v
  Kubernetes identity or an explicit unresolved reason
       |
       v
  authoritative namespace filter, then deterministic sampling
       |
       v
  temporary human-readable log line
#+end_example

The kernel side reports syscall facts and opaque bytes. Userspace reconstructs
those facts. Kubernetes enrichment belongs after reconstruction.

The accepted capture boundary is back at application =write= and =writev= on
stdout/stderr. A registered CRI-file tap was tested and rejected: it attributed
writes to the runtime, required descriptor discovery, and an inotify mistake
created a three-core rescan feedback loop. See the rejected
[[file:../spec/20260802-0928-userspace-registered-cri-log-tap.org][CRI log tap experiment]] and the accepted
[[file:../spec/20260803-1858-direct-kubernetes-identity.org][direct Kubernetes identity spec]].

Identity is layered off the hot path. The cgroup resolver maps the kernel
cgroup ID to a complete runtime container ID. One Kubernetes watch indexes Pods
assigned to this node by that exact container ID. Both publish snapshots; an
incoming event performs two memory lookups only. There is no CRI client,
runtime-socket mount, kubelet-log scan, or metadata I/O per event.

* 0. Refuse to hear ourselves

*Plain version.* Before turning on the microphone, put the microphone's own
room on the ignore list.

*Technical truth.* [[file:../boring-logtail/src/cgroup.rs][CollectorCgroup]] reads the cgroup-v2
membership from =/proc/self/cgroup=, validates the path, and opens the matching
directory below =/sys/fs/cgroup=. Userspace places that directory FD into slot
zero of the =COLLECTOR_CGROUP= cgroup array.

The eBPF entry program calls =current_task_under_cgroup(0)=. A matching task or
descendant is ignored. A helper error also means “do not capture this write.”
This is fail-closed because a broken self-filter can amplify one output line
forever.

*Why cgroup, not PID?* PID values change across namespaces. The original code
inserted container PID 1 while the tracepoint observed a host PID. Cgroup
membership is evaluated by the kernel against an open cgroup object, so the
namespace translation problem disappears.

* 1. Catch syscall entry

[[file:../boring-logtail-ebpf/src/main.rs][boring_logtail_enter]] runs at
=syscalls/sys_enter_write=.

It reads:

- numeric file descriptor
- userspace buffer address
- requested byte count
- current cgroup ID
- PID and TID
- monotonic timestamp

It first admits only numeric fd 1 or 2. Then it inserts a =WriteStart= into
=WRITE_STARTS= under the combined PID/TID key.

Namespace filtering currently happens after enrichment in userspace. A watch
limited to included namespaces cannot prove that a missing cgroup is excluded:
the included Pod may simply be newer than its status cache entry. Kernel
pushdown therefore remains deferred until exclusion can be established from
positive evidence without dropping an included container's first writes.

*Why remember instead of emit?* Entry only says what the application requested.
We need syscall exit to know whether Linux accepted all, some, zero, or none of
the bytes.

*Current sharp edge.* =WRITE_STARTS= has a fixed capacity. Insert failure drops
this observation. We do not yet expose a loss counter.

* 2. Pair syscall exit

[[file:../boring-logtail-ebpf/src/main.rs][boring_logtail_exit]] runs at
=syscalls/sys_exit_write=.

It reads the signed result, looks up the matching entry state, and removes that
state on every matched exit. It creates a =WriteJob= with chunk number zero,
stores it in =WRITE_JOBS=, then tail-calls the chunk worker.

An exit without entry state is ignored. That can happen when entry filtering or
state insertion rejected the operation.

* 3. Copy bounded chunks

The chunk worker asks [[file:../boring-logtail-common/src/lib.rs][next_write_chunk]] what piece comes
next. Current limits are:

#+begin_example
WRITE_CHUNK_SIZE      = 256 bytes
MAX_CHUNKS_PER_WRITE = 32
MAX_BYTES_PER_WRITE  = 8192 bytes
#+end_example

For each chunk it reserves one ring-buffer record, fills the metadata, attempts
=bpf_probe_read_user_buf()=, submits the event, increments the job, and
tail-calls itself again if needed.

The event says whether it is first, last, truncated, result-known, or affected
by a read failure. A failed or zero-byte syscall still produces one empty event
with the signed result. A write over 8192 bytes produces captured evidence with
a truncation marker.

*Important race.* The pointer came from syscall entry, but bytes are copied
after syscall exit. Another thread could mutate that userspace memory. The
current design reports what it managed to read, not a cryptographic snapshot of
the exact bytes Linux copied internally.

* 4. Cross the ring buffer

=EVENTS= is a 256 KiB BPF ring buffer. Each record has the fixed =WriteEvent=
layout defined in =boring-logtail-common=.

The userspace capture loop waits asynchronously for readability and drains all
available records. =decode_event= rejects the wrong byte size or ABI version and
performs an unaligned read into the shared C-layout type.

*Current sharp edge.* Ring-buffer reservation failure has no counter. That is an
explicit roadmap item, not an invisible promise.

* 5. Rebuild one write

[[file:../boring-logtail/src/pipeline.rs][WriteAssembler]] keys incomplete work by:

#+begin_example
(cgroup_id, pid, tid, operation_id)
#+end_example

It waits for a last or truncated chunk, then verifies:

- first-chunk marker exists
- all chunks belong to the same key
- stable metadata agrees
- byte offsets are contiguous
- nothing follows the terminal chunk

Success produces a =WriteOperation= containing timestamp, identity, syscall,
descriptor, requested length, actual result, integrity flags, and reconstructed
bytes.

*Why not call it a log yet?* One write can hold half a log line, several lines,
binary data, or a fragment of JSON. =WriteOperation= is one syscall, not one
application record.

*Current sharp edges.* Incomplete operations do not yet expire. Duplicate or
missing chunks become an error only when a terminal chunk lets assembly run.
=operation_id= currently reuses the entry timestamp; its collision guarantee is
not yet formally defined.

* 6. Frame, retain, and make temporary output

After reconstruction, =Pipeline= joins the current in-memory Kubernetes
identity snapshots, applies the immutable namespace filter, chooses an internal
framing lane, frames newline-delimited records, then samples complete records.
One write can finish zero, one, or many =LogRecord= values. Sampling after
framing cannot punch a hole into the middle of a line.

The framer preserves opaque bytes across write boundaries. One record is capped
at an internal 64 KiB safety bound. Container streams are
internal framing lanes so bytes from different containers or descriptors are
never joined. Aggregate pending bytes are derived from the store memory
envelope; pressure emits an integrity-marked fragment instead of silently
growing or discarding it. Kernel read failures become explicit capture gaps, so
bytes from opposite sides of missing evidence are never stitched into a fake
complete line.

Accepted records enter a bounded channel without blocking eBPF ring-buffer
drain. One Tokio task owns the in-memory store: one ring per workload UID, Pod
and namespace indexes, process-local sequence allocation, and subscribers. A
workload's =max_logs= count is shared by all current and historical Pod replicas;
every record keeps Pod UID and name. The global =max_memory= envelope can evict
globally oldest records before a workload reaches that count.

The current edge also renders one human-readable line:

#+begin_example
incoming_log source="k8s namespace=payments pod_uid=... container_id=... \
  stream=stdout-candidate" bytes=83 integrity=RecordIntegrity {...} \
  payload="{\"kind\":\"checkout\",\"order_id\":\"BLT-42\",...}\n"
#+end_example

Invalid UTF-8 is rendered with replacement characters for the terminal, while
the =LogRecord.bytes= value stays unchanged.

This output is deliberately temporary. Printing every node record is noisy and
creates observer effects. The cgroup filter prevents recursion; the future
network adapter still needs authentication, authorization, and a wire contract.

* The replay/live handoff

A subscription selector names a workload UID, Pod UID, or namespace.
The owner task chooses watermark =N=, snapshots matching retained records
through =N=, then registers live delivery before processing another append.
Replay followed by live delivery therefore has no duplicate or gap at that
boundary.

This is connected-session truth, not durable exactly once. Sequences reset on
restart, there are no acknowledgements or reconnect cursors, and retained
history can already have been evicted. Reading replay or live delivery removes
only the subscriber's reference; it never drains retained history. Slow
subscribers never stall capture, and overflow closes only that session with
=SubscriberLagged=.

* What “valuable data” means today

The live DaemonSet has already reconstructed:

- structured Flux reconciliation JSON
- GitLab Runner diagnostics
- ExternalDNS status
- controller-runtime warnings
- a deliberate =BLT-42= checkout signal

For each write we retain kernel cgroup identity, process/thread identity,
descriptor, byte length, integrity status, and payload. The enrichment join adds
exact node, namespace, Pod, and container identity when both snapshots know it,
and states an explicit reason when they do not.

* The Kubernetes enrichment boundary

Enrichment consumes =WriteOperation= rather than reaching backward into eBPF:

#+begin_example
WriteOperation
      |
      +--> resolve cgroup ID -> runtime container ID
      |
      +--> join node-local Pod cache
      |
      v
namespace, Pod, container, node + original capture facts
#+end_example

The userspace collector maintains two asynchronous snapshots. A host cgroup-v2
scan maps the kernel cgroup ID to an exact runtime-qualified container ID. A
node-filtered Kubernetes Pod watch maps that container ID to node, namespace,
Pod UID/name, and container name. The write path only reads those snapshots; it
never walks cgroupfs or calls Kubernetes while processing a write.

The kernel cannot know human Kubernetes names because those are control-plane
concepts, not Linux identities. The background cgroup scan and Pod watch are the
bridge. If either snapshot lacks an exact match, the bytes remain visible with
an unresolved reason instead of guessed metadata.

The human-facing line starts with =incoming_log=. Its =source= is deliberately
loud and exact:

#+begin_example
incoming_log source="k8s=payments/checkout-abc/checkout pod_uid=... node=worker-1 ..." ...
incoming_log source="k8s=unresolved reason=cgroup-not-indexed" ...
#+end_example

The first form distinguishes the incoming write by namespace, Pod, and
container. The second form keeps the bytes but refuses to fake attribution.
=stdout-candidate= and =stderr-candidate= mean only “observed on fd 1 or 2”; fd
tracking is still needed before those become durable stream identities.

Configuration is a versioned YAML file. No file means =filters: []= and a
100-percent sample. Kubernetes mounts the same safe default from a ConfigMap;
an allowlist creates one namespaced Pod watch per namespace while preserving
the =spec.nodeName= selector and one global Pod bound. Policy is immutable for
the process lifetime.

The Kubernetes deployment currently renders every admitted framed record. Sampling
happens after framing, so it never creates a partial line.
Each visible line carries the configured =sample_percent=. Local runs also
default to 100 percent unless =BORING_LOGTAIL_CONFIG= names a YAML file.

Sampling can also limit observer loops outside the collector's own
cgroup. On the live cluster, following collector output through =kubectl logs=
crosses konnectivity agents configured with =-v=8=. They log the transported
packets; the collector sees those new writes; another rendered record causes
more transport. Self-cgroup exclusion cannot stop that cross-cgroup cycle. A
low sampling percentage can make the loop subcritical, while source filtering
or lower agent verbosity is the real cure.

Disappeared cgroup mappings stay in a bounded five-minute retention cache.
Deleted Pods currently leave the Pod snapshot immediately; a late write is then
explicitly unresolved. The cgroup path decoder supports the measured containerd
and CRI-O cgroup-v2 layouts.

* Things we intentionally do not claim

- We capture =write= and bounded =writev=, not every route bytes can take.
- Numeric fd 1/2 is not durable stdout/stderr identity.
- We frame newlines, but do not interpret semantic multiline or JSON documents.
- Retained history is volatile and node-local; restart forgets it.
- Replay/live is gap-free only for one connected session, not durable exactly once.
- We do not yet quantify every loss boundary.
- We do not map unsupported runtime or cgroup layouts to Kubernetes identity.
- We do not promise every architecture or compatibility syscall ABI.

The [[file:../ROADMAP.org][roadmap]] keeps those debts visible.

** Store identity and bounds

Retention belongs to a resolved Kubernetes workload UID, not an FD or container
stream. A standalone Pod uses its Pod UID as its workload UID. One workload ring
interleaves all Pod replicas in store order; Pod metadata remains on each record.
Unresolved owner chains are rejected rather than guessed. Operators configure
only =max_memory=, =max_logs=, and =retention=. Retention accepts whole seconds,
minutes, or hours and expires each record from its monotonic store-admission
instant. Workload admission and the 64 KiB framing
limit are safety bounds derived or owned internally. Framing, ingress, replay,
and subscriber bounds are derived internally. Slow subscriber reads release only delivery references—they never
drain retained history. Severity remains =Unknown= until a classifier has
evidence; stdout/stderr is not evidence.

** Event catching without clogging capture

One compiled regex set sees complete, identity-accepted records before output
sampling. A match clones a tiny typed event into a bounded Tokio channel with
=try_send=. The Discord worker owns network I/O. If delivery slows down, its
queue fills and notifications are counted and dropped; log capture never waits
for the internet or a slow output stream. The stdout emitter renders one quoted,
escaped physical line; Discord performs HTTP delivery. Event messages are
static context, while every caught event shares the exact final =LogRecord=
that matched. Emitters therefore retain identity, provenance, timestamps,
integrity, severity, and bytes without maintaining a lossy shadow record.
Invalid UTF-8 is rendered explicitly as hexadecimal escapes instead of being
silently replaced.

The kernel timestamp is monotonic time since boot, not wall time. Record
finalization therefore adds one userspace UTC =observed_at= timestamp. Discord
uses it in a compact colored embed with only the caught log, namespace, Pod,
container, and stream. Internal IDs, sampling state, and the integrity debug
dump stay out of alerts; stdout remains the detailed diagnostic rendering.
