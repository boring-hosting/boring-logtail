* Status

Requested by the maintainer and completed on 2026-08-13.

* Goal

Bring the teaching style of =learn/= next to the code that needs it. A reader
who can read Rust should be able to understand what the non-obvious machinery
does, why it exists, what invariant it protects, and where the simplification
stops being true without first reverse-engineering the whole repository.

* Writing contract

- Start with the plain version, then state the exact mechanism.
- Explain why a boundary or data structure exists; do not translate obvious
  syntax into English.
- Put crate/module overviews in =//!=== docs, public API contracts in =///= docs,
  and local invariant explanations beside the relevant private code.
- Document failure and ambiguity paths, memory/backpressure ownership, and
  safety arguments around every non-trivial =unsafe= block.
- Keep comments small enough to remain readable beside code. Link to =learn/=
  for the longer walk rather than cloning whole chapters into Rust files.
- Preserve the project's terse, joyful voice and technical honesty.

* Scope

The audit covers every Rust source file. Deep explanations concentrate on:

- eBPF entry/exit pairing, maps, tail calls, bounded user-memory reads, and ABI
  emission;
- userspace write reconstruction, framing, sampling, and capture ownership;
- cgroup scanning plus the exact cgroup/container/Pod identity join;
- Kubernetes relists, stale snapshots, workload history, and ambiguity;
- store memory partitions, admission permits, retention, replay/live handoff,
  subscriber isolation, and shutdown;
- model stage vocabulary and why values are shared through =Arc=;
- emitter queues, failure isolation, Discord safety, and stdout escaping; and
- the transport-free API façade and application composition root.

Tests receive comments only where a fixture proves an invariant that is not
obvious from its name. Generated API documentation must build with warnings
denied and no broken intra-doc links.

* Acceptance

- Every crate and substantial application module has a useful plain-first
  overview with a pointer to the relevant field-guide page.
- Every public domain/store/API/emitter type and non-obvious public operation
  explains its purpose and important ownership or failure semantics.
- Complex private state machines and memory/accounting choices have nearby
  “why” comments.
- Every production =unsafe= block has a specific safety explanation.
- Inline claims agree with =learn/=; any discovered mismatch is repaired in the
  same TODO item.
- Documentation adds no behavior change and avoids commentary on obvious code.
- Rustdoc, workspace tests, strict userspace and eBPF Clippy, formatting,
  field-guide link checks, and diff checks pass.
