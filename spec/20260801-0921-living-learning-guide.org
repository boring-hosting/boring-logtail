* Goal

Create a living =learn/= field guide for the Linux, eBPF, and boring-logtail
concepts a curious human needs to understand this project. Explain each idea in
clean everyday language without throwing away the technical machinery that
makes the explanation true.

* Audience

A developer who can read code but does not yet carry the Linux kernel, cgroup,
or eBPF execution model in their head. The guide should also remain useful as a
quick glossary for experienced contributors.

* Voice and teaching shape

- Begin with the dumbified version: one or two sentences and a concrete image.
- Follow with the technical truth: exact names, boundaries, identifiers, and
  failure modes.
- End with why boring-logtail cares and links to the relevant source/spec.
- Prefer small examples, ASCII/Org diagrams, and commands a reader can inspect.
- Say when an analogy stops being true.
- Keep the project's joyful hacker voice. No courseware voice, corporate fog,
  or unexplained acronym soup.
- Never simplify a statement into something technically false.

* Structure

** =learn/README.org= — map of the rabbit hole

The entry point, suggested reading order, current-project snapshot, and links to
every guide. It explains how pages are maintained and licensed.

** =learn/linux.org= — the ground beneath us

Kernel space versus userspace, processes and threads, syscalls, file
descriptors, writes and partial writes, PID namespaces, cgroup v2, procfs,
tracefs, stdout/stderr, pipes, and why descriptor number is not stream identity.

** =learn/ebpf.org= — tiny programs in a very suspicious kernel

Programs, hooks/tracepoints, verifier, helpers, maps, ring buffers, tail calls,
bounded work, CO-RE versus this project's build approach, GPL declarations,
and the kernel/userspace ABI.

** =learn/boring-logtail.org= — how this beast hears logs

Walk the current path from =sys_enter_write= through =sys_exit_write=, chunking,
ring-buffer transport, =WriteAssembler=, =WriteOperation=, integrity markers,
self-exclusion through cgroups, and the future enrichment boundary. Clearly
label what exists now versus what is planned.

** =learn/glossary.org= — words without gatekeeping

An alphabetical quick reference for every important Linux, eBPF, Rust, logging,
and kubernetes term used by the current project. Each entry links back to the
deeper guide and, where helpful, source code.

** =learn/lab.org= — poke it and see

Safe, short experiments for observing PIDs, cgroups, file descriptors, partial
writes, the live DaemonSet, and captured payload metadata. Commands distinguish
read-only inspection from actions that deploy or create temporary workloads.

* Maintenance contract

- Add an =AGENTS.md= workflow rule: any change introducing or materially
  changing a Linux/eBPF/project concept must update the relevant =learn/= page
  in the same spec TODO and visible task plan.
- Link =learn/README.org= from the root README without bloating the README.
- All pages use Org mode and =GFDL-1.3-or-later= with no invariant sections.
- Source links are relative and point at current repository boundaries rather
  than brittle generated line numbers.

* Non-goals

- A complete Linux, Rust, kubernetes, or eBPF textbook.
- Copying external manuals into the repository.
- Pretending planned behavior already exists.
- API reference generated from Rust documentation.

* Verification

- Every =learn/*.org= file declares its title and documentation license.
- Every local =file:= link resolves.
- The glossary covers every emphasized term in the four narrative guides.
- Claims about current behavior are checked against eBPF, common ABI,
  userspace, Skaffold, and kubernetes source files.
- Commands are syntax-checked where practical and destructive commands carry a
  warning.
- Org source blocks and links are mechanically audited.
